# Garage とバックアップの外部監視

## 目的と範囲

単一の物理ホスト・Garage VM で、データ保全に影響する障害に Discord から気づけるようにする。連続稼働は目的としない。既存の Garage、R2 バックアップと Tunnel を使い、監視のための新しい外部サービスは追加しない。

## 方式の比較

- Worker が VM を pull: 停電やホスト停止もホスト外から検知でき、容量や状態も確認できる。外部での判定と通知状態の管理が必要。
- VM から定期 push: バックアップの完了を伝えやすいが、連絡が途絶えたことを判定する外部の仕組みが必要。
- 同じ物理ホストに Prometheus と Alertmanager: 標準的で履歴も扱いやすいが、ホスト故障時に監視も止まる。

Worker から pull する方式を採用する。Prometheus 形式の node_exporter を使い、必要な指標に絞る。履歴やダッシュボードは今回の必須要件にしない。

## 構成

1. data-store VM の localhost に node_exporter を置き、ファイルシステム容量と Garage の systemd 状態を取得する。systemd collector の取得対象を必要な unit に絞る。
2. root の専用 timer が既存のバックアップ成功マーカーを 5 分ごとに読み、成功時刻を textfile collector 用の専用ディレクトリに原子的に書き出す。root 専用ディレクトリの権限は変更しない。成功記録が存在しない状態を未確認として通知する。監視用記録の作成はバックアップ本体と独立しており、失敗しても同期を妨げない。
3. 既存 Tunnel に監視用ホスト名から localhost の exporter へ向かう HTTP ルートを追加する。Cloudflare Access のサービス認証を必須にし、Worker にだけ必要な認証情報を渡す。Garage の既存 TCP ルートは維持する。
4. Cloudflare Worker の Cron Trigger が 5 分ごとに取得し、D1 に前回状態を記録して Discord に異常・復旧を通知する。Access のリダイレクト、HTTP エラー、タイムアウト、不正なメトリクス、必須項目の欠落を正常と判定しない。Webhook の失敗時に通知済みと記録しない。通知の重複は完全には排除できない。
5. ホスト側の ZFS pool の健全性と空き容量を追加する。VM の状態だけではミラーの片系故障を検知できないため、ホストで権限を絞った取得方法を確認する。

## 初期の判定

- 通信・Garage: 一時的な失敗による通知を減らすため、連続 3 回異常なら通知し、正常に戻れば復旧を通知する。
- VM と ZFS pool の容量: 残り 15% 未満を初期の警告値とし、実容量を通知に含める。ZFS の判定対象は現物の pool を確認する。
- バックアップ: 最終成功から 7 日と 12 時間を超えたら通知する。日曜 03:30 JST 開始、最大 30 分の開始遅延と直近約 4 時間の実行時間を考慮した初期値。初回成功前の記録なしは未確認であり、正常にはしない。
- バックアップの成功は復元の保証ではない。復元試験と保持方式の改善は既存の復旧計画で扱う。

## 安全性と確認

認証情報や Discord Webhook は Git、ログ、通知文に出さない。Worker のシークレットと既存の Vault を使い、Access の有効期限も管理する。Tunnel が停止している場合、Worker は到達不可を通知できるが、停電、回線、Tunnel、Access のいずれが原因かは断定できない。Cloudflare 自体の障害は同じ Cloudflare 上の Worker では必ずしも検知できない。

デプロイ前に Ansible の構文と check mode、Worker の判定・状態遷移のテストを実施する。設定後に正常時の値、認証なしのアクセス拒否、停止・バックアップ期限切れ・復旧時の通知、Discord 送信失敗後の再試行を確認する。実バックアップを停止せずに検証できる方法を優先する。監視自体の障害に備えて、定期的に通知試験を行う。

## 事前確認

- 既存の Cloudflare アカウントと Tunnel の設定権限、Workers と D1 の利用可否、Discord Webhook の設定方法を確認する。
- node_exporter の Debian パッケージ設定、VM と Proxmox の監視対象、Cloudflare 側のルート管理方法を確認する。
- バックアップ成功記録は次回成功まで存在しないため、導入直後は未確認として扱う。
