# Garage の backup のあるべき形

2026-11-17。PI 了承。

## 起きたこと

2026-11-08 と 11-15 の週次の backup（Garage の `dvc` bucket → R2、rclone `copy --immutable`）が `immutable file modified` で止まった。原因は R2 の写しの 1 つが 7 月の時点で途中で切れていたこと（元 4.72 GB に対し 2.46 GB、md5 が DVC の名前と不一致）。11-06 に Garage 側に正しい中身が入り直し、immutable の比較に掛かった。その写しは 7 月から復元できない状態だったが、大きさと時刻しか比べていなかったので気づかなかった。監視は 11-12 に「最終成功から 180 時間」を 1 回だけ通知し、その後は黙っていた。

## 目標

R2 から全 object を正しい中身で戻せること。戻せなくなったら数日以内に気づけること。

## あるべき形

1. **書き換えない copy は残す。** 誤操作やランサムウェアで backup が上書きされるのを防ぐ。DVC の object は中身が変わらないので、`immutable file modified` は正常な更新ではなく、どちらかが壊れた印として扱う。正しい側は DVC の名前（中身の md5）と一致する側。壊れた写しは trash に移して入れ直す。
2. **書いたあとの確かめは足さない（PI、過剰にしない）。** rclone は upload ごとに大きさを確かめ、切れたまま成功にはしない。7 月の写しは今の仕組みの前の初回構築の名残。2026-11-17 に全件の大きさを 1 回だけ突き合わせて棚卸しする。中身の確かめは 4 の復元の試験で DVC の名前（md5）と照らして行い、新しい hash は作らない。
3. **失敗をすぐ知らせ、直るまで知らせ続ける。** backup の service の失敗をその回のうちに通知する（今は最終成功からの経過時間だけで、最大 7.5 日遅れる）。直るまで 1 日 1 回通知し直す。
4. **復元の試験は全件を、名前と照らして通す。** 戻した object の md5 を DVC の名前と比べる。R2 の一覧との一致では、壊れた写しも一致してしまう。2026-11-04 の試験は、R2 から戻したものと R2 自身を `rclone check --download` で比べていた（`standards/data-store-restore.md`）。両方が同じ壊れた写しなので「全 622,859 件一致」になり、今回の object を見逃した。四半期に 1 回。
5. **写しの数。** 今は Garage（1 台のホスト、ZFS ミラー）と R2 の 1 か所。壊れた写しを直せる元が Garage しかない。もう 1 か所足すかは、量と費用を見て後で決める。

## 順

1. 今の 1 件を直す（R2 の壊れた写しを trash に移し、backup を手で流す）。
2. 全件の大きさの突き合わせ（1 回だけの棚卸し）の結果を見る。
3. 監視を小さく直す（backup の service の失敗をすぐ通知、直るまで 1 日 1 回通知し直す）。
4. 次の復元の試験で、戻した object の md5 を DVC の名前と照らす。
